* Overview

=gst-kyutaistt= is a GStreamer element that performs speech-to-text using
[[https://huggingface.co/kyutai][Kyutai STT]] models.  It is written entirely in Rust (no Python dependency)
and is designed as a drop-in replacement for =whispertranscribe=, sharing the
same pad caps, JSON output format, and signal interface.

Inference runs through [[https://github.com/huggingface/candle][Candle]] (Meta's Rust ML framework).  Audio
tokenisation uses the Mimi codec.  Text decoding uses SentencePiece (C++,
compiled natively via =sentencepiece-sys=).  *Zero Python at build-time or
run-time.*

** Available models

| Repository                   | Parameters | Languages       |
|------------------------------+------------+-----------------|
| =kyutai/stt-1b-en_fr-candle=   | 1 B        | English, French |
| =kyutai/stt-2.6b-en-candle=    | 2.6 B      | English         |

Models are downloaded automatically from HuggingFace Hub on first use.

* Building

** Prerequisites

- Rust toolchain (stable, edition 2021+)
- GStreamer 1.14+ development headers
- CMake (for sentencepiece-sys)
- pkg-config

On Debian/Ubuntu:

#+begin_src sh
apt-get install libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev \
               cmake pkg-config
#+end_src

** Compile

#+begin_src sh
cd gst-kyutaistt
cargo build --release
#+end_src

For GPU acceleration, add a feature flag:

#+begin_src sh
cargo build --release --features cuda    # NVIDIA CUDA
cargo build --release --features cudnn   # NVIDIA cuDNN
cargo build --release --features metal   # Apple Metal
#+end_src

The output is a shared library: =target/release/libgstkyutaistt.so= (Linux)
or =libgstkyutaistt.dylib= (macOS).

** Install

#+begin_src sh
# System-wide
cp target/release/libgstkyutaistt.so /usr/lib/x86_64-linux-gnu/gstreamer-1.0/

# Or per-session
export GST_PLUGIN_PATH=$PWD/target/release
#+end_src

Verify:

#+begin_src sh
gst-inspect-1.0 kyutaistt
#+end_src

* Usage

** Basic file transcription

#+begin_src sh
gst-launch-1.0 \
  filesrc location=audio.wav ! decodebin ! audioresample ! audioconvert \
  ! "audio/x-raw,format=F32LE,rate=24000,channels=1" \
  ! kyutaistt model=kyutai/stt-1b-en_fr-candle \
  ! fakesink dump=true
#+end_src

** Microphone input (PulseAudio)

#+begin_src sh
gst-launch-1.0 \
  pulsesrc ! audioconvert ! audioresample \
  ! "audio/x-raw,format=F32LE,rate=24000,channels=1" \
  ! kyutaistt model=kyutai/stt-1b-en_fr-candle enable-vad=true \
  ! fakesink dump=true
#+end_src

** With resampling (48 kHz input)

The element accepts 8/16/22.05/24/44.1/48 kHz input and resamples internally
to 24 kHz.  Preferred input is 24 kHz F32LE mono (zero-copy path).

#+begin_src sh
gst-launch-1.0 \
  filesrc location=recording_48k.wav ! decodebin ! audioresample \
  ! "audio/x-raw,format=F32LE,rate=48000,channels=1" \
  ! kyutaistt \
  ! fakesink dump=true
#+end_src

** CPU-only mode

#+begin_src sh
gst-launch-1.0 \
  filesrc location=audio.wav ! decodebin ! audioresample ! audioconvert \
  ! "audio/x-raw,format=F32LE,rate=24000,channels=1" \

* Pads

** sink (ALWAYS)

Audio input pad.  Accepts raw audio; internally resampled and downmixed to
24 kHz mono for model processing.

#+begin_example
audio/x-raw,
    format   = { F32LE, S16LE },
    rate     = { 8000, 16000, 22050, 24000, 44100, 48000 },
    channels = { 1, 2 }
#+end_example

Preferred negotiation: =F32LE, rate=24000, channels=1=.  Other
rates/channels are accepted but converted internally.

| Format | Bytes/sample/channel | Notes                           |
|--------+----------------------+---------------------------------|
| F32LE  |                    4 | Preferred, no conversion needed |
| S16LE  |                    2 | Converted to float internally   |

** src (ALWAYS)

JSON transcription output pad.  Each buffer contains a JSON object with
transcription segments.

#+begin_example
application/x-json-transcription,
    format = whisper
#+end_example

Output buffer allocation: 64 KB per transform call.

*** JSON Output Format

Each output buffer contains a JSON object with transcription segments:

#+begin_src json
{
  "segments": [
    {
      "text": "transcribed text here",
      "start_time": 1.234,
      "end_time": 1.567,
      "confidence": 1.0,
      "language": "auto",
      "tokens": [
        {
          "text": "transcribed",
          "prob": 1.0,
          "start_ms": 1234,
          "end_ms": 1567,
          "start_sample": 29616,
          "end_sample": 37608
        }
      ]
    }
  ]
}
#+end_src

When no words are produced for a given buffer, the output is:

#+begin_src json
{"segments":[]}
#+end_src

** ctrl (REQUEST)

Optional control pad for runtime commands.  Created on demand; at most one
ctrl pad exists at a time.

#+begin_example
application/x-whisper-control
#+end_example

*** Control Commands

JSON messages pushed to the ctrl pad:

#+begin_src json
{ "command": "set_language", "language": "fr" }
#+end_src

Created via =gst_element_request_pad()= or autoplugging.  Released via
=gst_element_release_request_pad()=.

* Architecture

** Source Layout

#+begin_example
gst-kyutaistt/
├── Cargo.toml       # cdylib crate; depends on gstreamer 0.23 + candle/moshi
├── Cargo.lock       # Pinned dependencies
├── build.rs         # gst-plugin-version-helper
└── src/
    ├── lib.rs       # Plugin registration (element name: "kyutaistt")
    ├── imp.rs       # GstElement implementation (BaseTransform subclass)
    ├── model.rs     # Kyutai STT model wrapper (adapted from stt-rs)
    └── vad.rs       # Energy-based pause / turn-taking detector
#+end_example

** Processing Pipeline

1. *Format conversion* — S16LE samples are converted to F32LE.
2. *Downmix* — Stereo input is averaged to mono.
3. *Resampling* — Non-24kHz input is resampled via [[https://crates.io/crates/rubato][rubato]] (FFT-based).
4. *Chunking* — Audio is accumulated and processed in 1920-sample chunks
   (80 ms at 24 kHz), which is the model's native step size.
5. *Pause detection* — Energy-based RMS analysis with debounced
   speech/silence transitions, boundary detection, and turn-end heuristics.
6. *Mimi tokenisation* — PCM is encoded into discrete audio tokens by the
   Mimi neural codec.
7. *Transformer inference* — Audio tokens are processed by the causal
   transformer LM, which outputs text tokens and (optionally) VAD
   probabilities at multiple time horizons.
8. *SentencePiece decoding* — Text token IDs are decoded to Unicode text
   with word boundaries and timing information.
9. *JSON serialisation* — Words are formatted into the whisper-compatible
   JSON schema and written to the src pad buffer.

** State Machine

#+begin_example
  NULL ──► READY ──► PAUSED ──► PLAYING
   │         │                     │
   │    model loaded          inference runs
   │    (HF Hub download)     (chunk-by-chunk)
   │         │                     │
   ◄─────────┘                     │
  READY ◄── PAUSED ◄── PLAYING ◄───┘
   │
   ▼
  NULL (model unloaded)
#+end_example

- *NULL → READY*: Model is downloaded from HuggingFace Hub (if not cached)
  and loaded into memory.  Signals =model-loaded= and =model-info= are
  emitted.  On failure, =model-load-failed= is emitted and the state
  transition fails.
- *READY → NULL*: Model is unloaded.  Signal =model-unloaded= is emitted.
- *EOS*: Remaining audio is flushed through the model by feeding silence
  to ensure all pending words are emitted.

** Dual VAD System

The element provides two complementary VAD mechanisms:

1. *Neural VAD* (=enable-vad=) — The Kyutai STT model's built-in VAD head
   predicts no-speech probability at 4 time horizons (~0.5s, ~1s, ~2s,
   ~3s).  The 2-second horizon is used as the primary signal.  This is
   semantic-level VAD that understands speech content.

2. *Energy-based VAD* (=enable-pause-detection=) — RMS energy analysis with
   configurable hysteresis for debounced speech/silence transitions.  This
   drives the =speech-start=, =speech-end=, =pause-detected=,
   =boundary-detected=, and =turn-end= signals.

Both can be enabled simultaneously for maximum signal richness, or
individually depending on the application.

* Latency

** Transcription Latency

End-to-end latency from spoken word to transcribed text depends primarily on
the model's *algorithmic delay* (=asr_delay_in_tokens=), not GPU speed.  The
model intentionally looks ahead by N tokens before committing to text output,
trading latency for accuracy.

| Component             | 1B (en/fr)  | 2.6B (en)     | Notes                                     |
|-----------------------+-------------+---------------+-------------------------------------------|
| Audio chunk           | 80 ms       | 80 ms         | 1920 samples @ 24 kHz, fixed              |
| Mimi tokeniser        | ~1 ms       | ~1 ms         | Small convolutional codec, trivial on GPU |
| Algorithmic delay     | *480 ms*      | *2560 ms*       | 6 × 80 ms vs 32 × 80 ms                   |
| Transformer forward   | ~2–4 ms     | ~5–10 ms      | Single causal step with KV cache          |
| Word assembly         | 0–160 ms    | 0–160 ms      | Word emitted when next word starts        |
|-----------------------+-------------+---------------+-------------------------------------------|
| *Total (spoken → text)* | *~560–640 ms* | *~2640–2720 ms* |                                           |

The algorithmic delay is set by =asr_delay_in_tokens= in the config:

- *1B model*: =asr_delay_in_tokens = 6= → 6 × 80 ms = 480 ms
- *2.6B model*: =asr_delay_in_tokens = 32= → 32 × 80 ms = 2560 ms

GPU performance (e.g. RTX 3060 vs RTX 5090) affects only the transformer
forward pass (~2–10 ms), which is negligible compared to the algorithmic delay.

** Turn-End Detection Latency

Two complementary mechanisms detect when a speaker has finished their turn:

*** Energy-based turn-end

The energy-based pause detector (=vad.rs=) fires =turn-end= after sustained
silence following speech.  Default timing:

| Stage                  | Duration | Configurable via          |
|------------------------+----------+---------------------------|
| Silence hysteresis     | 150 ms   | =signal-silence-hysteresis= |
| Turn silence threshold | 500 ms   | =turn-silence-threshold=    |
|------------------------+----------+---------------------------|
| *Total from last speech* | *~650 ms*  |                           |

Requirements: silence ≥ =turn-silence-threshold= (500 ms) after speech ≥
=min-turn-speech-duration= (200 ms).

*** Neural (semantic) turn-end

The model's extra heads predict no-speech probability at 4 time horizons.
The 2-second horizon (index 2) is the primary turn-end signal:

| Horizon index | Look-ahead | Purpose             |
|---------------+------------+---------------------|
|             0 | ~0.5 s     | Immediate           |
|             1 | ~1.0 s     | Short-term          |
|             2 | ~2.0 s     | *Primary turn signal* |
|             3 | ~3.0 s     | Long-term           |

The signal fires when =prs[2] > no-speech-threshold= (default: 0.6).

Because the neural VAD runs through the transformer, the algorithmic delay
applies.  Expected latency from last speech:

| Model | Algorithmic delay | Neural turn-end latency |
|-------+-------------------+-------------------------|
| 1B    | 480 ms            | ~560–720 ms             |
| 2.6B  | 2560 ms           | ~2.6–3.0 s              |

The semantic VAD is more accurate than energy-based detection — it
understands linguistic context and can distinguish intentional pauses
(e.g. mid-sentence thinking) from actual turn endings.

*** Combined behaviour

When both systems are enabled, the earliest signal wins.

| Model | Energy turn-end | Neural turn-end | First signal     |
|-------+-----------------+-----------------+------------------|
| 1B    | ~650 ms         | ~560–720 ms     | ~560–650 ms      |
| 2.6B  | ~650 ms         | ~2.6–3.0 s      | ~650 ms (energy) |

For the *1B model*, both signals arrive at roughly the same time, providing
high-confidence turn detection.  For the *2.6B model*, the energy-based
signal fires first; the neural signal can be used as a delayed confirmation.

*** Tuning for lower latency

To reduce turn-end latency at the cost of more false positives:

- Lower =turn-silence-threshold= (e.g. 300 ms instead of 500 ms)
- Lower =signal-silence-hysteresis= (e.g. 80 ms instead of 150 ms)
- Lower =no-speech-threshold= (e.g. 0.4 instead of 0.6)

For voice agents, the 1B model is recommended — it provides ~560–650 ms
turn-end latency with semantic understanding, which is sufficient for
responsive conversational interaction.

* Differences from whispertranscribe

| Aspect             | whispertranscribe          | kyutaistt                          |
|--------------------+----------------------------+------------------------------------|
| Backend            | whisper.cpp (C++)          | Candle + Moshi (Rust)              |
| Model format       | GGUF files (local)         | SafeTensors / GGUF (HuggingFace)   |
| Model property     | =model= (filepath)           | =model= (HF repo ID)                 |
| Native sample rate | 16 kHz                     | 24 kHz                             |
| Streaming          | Sliding window + consensus | Native streaming (80ms chunks)     |
| VAD                | Silero VAD (ONNX)          | Built-in neural VAD head           |
| Python dependency  | None (C++)                 | None (Rust)                        |
| GPU support        | Via whisper.cpp            | CUDA, cuDNN, Metal (compile flags) |
| Quantisation       | GGUF built-in              | GGUF support via Candle            |

The element is pad-compatible: same sink caps, same src caps
(=application/x-json-transcription,format=whisper=), same ctrl pad caps,
same signal names and parameter types.  Existing pipelines can switch
backends by replacing =whispertranscribe= with =kyutaistt= and adjusting the
=model= property.

* Training New Language Models

The 1B architecture can be retrained or fine-tuned for additional languages.
This section documents the hardware requirements and expected performance
trade-offs for each approach.

** Architecture Summary (1B variant)

| Component             | Value                          |
|-----------------------+--------------------------------|
| Transformer layers    | 16                             |
| Hidden dimension      | 2048                           |
| Attention heads       | 16                             |
| FFN dimension         | 8192                           |
| Audio codebooks       | 32 (Mimi encoder)              |
| Text vocabulary       | 8000 tokens (SentencePiece)    |
| Context window        | 750 tokens                     |
| Audio token rate      | 12.5 tokens/sec (80 ms chunks) |
| Norm                  | RMSNorm, pre-norm              |
| Position encoding     | RoPE                           |

The audio side (Mimi codec) is language-independent — it encodes acoustic
features regardless of language.  All language-specific knowledge lives in
the transformer weights and the text tokeniser.  This means you do *not*
need to retrain the audio encoder.

** What Needs to Change Per Language

1. *SentencePiece tokeniser* — retrain on target-language text (trivial,
   runs in minutes on CPU)
2. *Text embeddings* — reinitialise the input embedding (8001 × 2048) and
   output projection (2048 × 8000), ~32M parameters total
3. *Transformer weights* — fine-tune or train from scratch

The Mimi audio codec is reused as-is.

** Hardware Requirements

*** Full training from scratch

Train the entire 1B transformer on paired audio/transcript data from
scratch.

| Resource        | Recommendation              |
|-----------------+-----------------------------|
| GPUs            | 4–8× A100-80GB or H100-80GB |
| VRAM per GPU    | 80 GB                       |
| Interconnect    | NVLink or InfiniBand        |
| Training data   | 5,000–50,000 hours          |
| Training time   | Days to weeks               |

*Expected quality*: Best possible — the model learns the target language's
phonetics, prosody, and grammar from the ground up.  This is what Kyutai
did for the released en/fr model.

*When to choose this*: When you have ≥10,000 hours of high-quality
transcribed speech and want maximum accuracy.

*** Full fine-tune from existing checkpoint

Start from the en_fr checkpoint, swap the tokeniser and text
embeddings, and fine-tune all transformer weights.

| Resource      | Recommendation                 |
|---------------+--------------------------------|
| GPUs          | 1–2× A100-80GB or 1× H100-80GB |
| VRAM per GPU  | 40–80 GB                       |
| Training data | 1,000–10,000 hours             |
| Training time | Hours to days                  |

*Expected quality*: Very good.  The transformer has already learned
general speech-to-text mappings from English/French; it transfers well to
related languages (e.g. Spanish, German, Italian) and reasonably well to
more distant ones (e.g. Mandarin, Arabic) given enough data.  Expect
5–15% higher WER than from-scratch training at the same data scale, but
dramatically less compute.

*When to choose this*: The recommended default for most new languages.
Best balance of quality, cost, and turnaround time.

*** LoRA / QLoRA fine-tune

Freeze most weights and train low-rank adapters (rank 16–32) on top.

| Resource      | Recommendation              |
|---------------+-----------------------------|
| GPUs          | 1× RTX 4090 / A6000 (24 GB) |
| VRAM per GPU  | 16–24 GB                    |
| Training data | 100–500 hours               |
| Training time | Hours                       |

*Expected quality*: Good for well-resourced languages where the
pre-trained model already has some cross-lingual transfer.  Expect
15–30% higher WER than full fine-tuning.  May struggle with
phonologically distant languages or heavily accented speech.

*When to choose this*: Quick prototyping, low-resource languages where
you have limited data, or when you only have consumer GPU hardware.

** Expected Performance Comparison

| Scenario       | Relative WER | Compute cost | Data needed   | Turnaround | Best for                     |
|----------------+--------------+--------------+---------------+------------+------------------------------|
| From scratch   | 1.0× (best)  | $$$$         | 5K–50K hours  | Weeks      | Production, maximum quality  |
| Full fine-tune | 1.05–1.15×   | $$           | 1K–10K hours  | Days       | Most new languages (default) |
| LoRA fine-tune | 1.15–1.30×   | $            | 100–500 hours | Hours      | Prototyping, budget hardware |

Notes:
- WER = Word Error Rate; lower is better.  "1.0×" = baseline from-scratch.
- Real WER depends heavily on language, domain, and data quality.
- Languages phonologically close to English/French (e.g. Spanish, German)
  benefit most from transfer learning.
- Tonal languages (Mandarin, Vietnamese) or agglutinative languages
  (Turkish, Finnish) may need more data and benefit less from transfer.

** VRAM Breakdown (Full Fine-Tune, bf16)

For a single-GPU full fine-tune, the memory budget is roughly:

| Component              | Size      |
|------------------------+-----------|
| Model weights (bf16)   | ~2 GB     |
| Gradients (bf16)       | ~2 GB     |
| AdamW optimizer states | ~8 GB     |
| Activations (batch=1)  | ~4–8 GB   |
| Activations (batch=16) | ~20–40 GB |
| Framework overhead     | ~2–4 GB   |
|------------------------+-----------|
| *Total (batch=1)*        | *~18 GB*    |
| *Total (batch=16)*       | *~40 GB*    |

With gradient checkpointing, activation memory can be reduced ~3× at the
cost of ~30% slower training.

** Data Sources

Good multilingual speech corpora for training:

- [[https://commonvoice.mozilla.org/][Mozilla Common Voice]] — crowd-sourced, 100+ languages, variable quality
- [[https://www.openslr.org/94/][Multilingual LibriSpeech (MLS)]] — read speech, 8 languages, high quality
- [[https://github.com/facebookresearch/voxpopuli][VoxPopuli]] — European Parliament, 23 languages
- [[https://ai.google/tools/datasets/fleurs/][FLEURS]] — Few-shot evaluation set, 102 languages (small but diverse)
- [[https://openslr.org/12/][LibriSpeech]] — English only, gold standard for benchmarking

The hardest part is not compute — it is getting *high-quality aligned
audio/transcript pairs* at scale for the target language.

** Inference Cost After Training

All training scenarios produce a model with identical inference
characteristics: same 1B architecture, same 80 ms chunk latency, same
VRAM footprint (~2–4 GB).  The training method affects only accuracy,
not runtime performance.
